# Haben-Update vorbereiten

Die Update-Auslösung ist derzeit **deaktiviert** und lässt sich auch nicht durch eine Umgebungsvariable einschalten. Vor einer späteren Freigabe muss der Kandidatenarbeitsbereich auf ein getrenntes Dateisystem mit harter Speicherquote gelegt und die Quote tatsächlich geprüft werden. Erst anschließend darf die feste Sperre im Code entfernt werden. Die Einstellungen zeigen diese Grenze an.

Die vorbereitete Implementierung würde einen isolierten Kandidaten vom festen Ursprung `https://github.com/firsttris/haben.git`, Branch `main`, laden. Der Lauf klont nur Quelltext und wendet anschließend die Videomaker-Patches aus `apps/buchhaltung/.videomaker/patches` an. Er führt keinen Code des Kandidaten aus, installiert nichts und ändert keine Datenbank. Ein Erfolg bedeutet **nicht**, dass Build, Migrationen, Anwendungen oder Funktionen getestet wurden. Die kontrollierte Übernahme mit Sicherung, Tests und Rückweg ist noch nicht automatisiert. Bei Patchkonflikten wird ein Fehler angezeigt; der Kandidat muss durch eine Entwicklerin oder einen Entwickler geprüft werden.

Zugriff und Auslösung benötigen eine Videomaker-Anmeldung; POST verlangt zusätzlich die konfigurierte gleiche Origin. Der Worker erhält weder Umgebungsvariablen des Dienstes noch seine Zugangsdaten. Statusmeldungen enthalten keine Git-Ausgaben. Der exklusive Ordner `DATA_DIR/haben-updates/running` verhindert parallele Läufe auch über mehrere Serverprozesse. Kandidaten und Status liegen ausschließlich in `DATA_DIR/haben-updates`; es werden höchstens zwei Kandidaten behalten, damit sie geprüft werden können. Sie werden nicht automatisch gelöscht.

Der Server benötigt `/usr/bin/git`, `/usr/bin/prlimit` und Zugriff auf GitHub. Je Git-Prozess sind 128 MiB pro Datei erlaubt. Der Worker prüft den Kandidaten ungefähr alle 500 ms auf höchstens 256 MiB Gesamtgröße und mindestens 1 GiB verbleibenden Speicher; vor jedem Aufruf muss zusätzlich Platz für den ganzen Kandidaten vorhanden sein. Diese Überwachung ist kein Dateisystem-Quota: Zwischen den Messungen oder durch andere Prozesse kann das Limit überschritten werden. Für eine harte räumliche Isolation ist ein eigenes Dateisystem mit Quota erforderlich. Wenn eine Grenze erreicht wird oder ein Git-Prozess länger als drei Minuten läuft, stoppt der Worker dessen Prozessgruppe. Bei nicht sicher beendetem Prozess bleibt die Sperre bestehen. Ein abrupter Serverabsturz kann ebenfalls eine Sperre hinterlassen.

Bei einem ungeklärten Lauf den Dienst stoppen, alle noch laufenden Git-/Remote-Prozesse des betreffenden Workers sicher beenden und das Update-Verzeichnis untersuchen. Die Sperre erst dann entfernen, wenn sicher kein solcher Prozess mehr arbeitet. Kandidaten nur nach Prüfung archivieren oder gezielt löschen. Keine Produktionsdatenbank und keine anderen Datenverzeichnisse verändern. Bei wenig freiem Speicher wird die Vorbereitung abgelehnt. Statusmeldungen sind bewusst allgemein; zur Fehleranalyse die Integrationspatches und den isolierten Kandidaten prüfen.
